## 二、发现的问题（按严重性）

### P0：引擎与 iSH 之间没有执行通道

这是比「boot 未接线」更深一层的断点。

**链路追踪**：

```
工具层 tools/src/lib.rs:429
  → Arc::new(IshLinuxBackend::new(...))            ← 接上了
  → IshLinuxBackend::command()  services/src/runtime.rs:435
      → 返回 RuntimeCommand { program, args, env, cwd }   ← 只是描述，没执行
  → RuntimeCommand::into_tokio()  services/src/runtime.rs:274
      → tokio::process::Command::new(program).spawn()     ← ❌ iOS 禁止 fork/exec
```

**证据**：

```
$ grep -r 'coomi_ish_run' apps/coomi-rs/
（0 处 —— Rust 侧完全不知道 iSH 桥接函数的存在）
```

引擎只导出三个 C 函数：`coomi_start` / `coomi_port` / `coomi_version`
（`ui/src/ios_ffi.rs:62/136/142`）。**没有任何 shell 执行入口。**

**后果**：iOS 上任何需要执行外部命令的工具（shell / git / python / ffmpeg …）
都会在 `spawn()` 处失败。`IshLinuxBackend` 目前只是一个「产出同样数据结构」的
适配器，它描述的 `RuntimeCommand` 最终仍走 POSIX 子进程。

**这不是本次改动引入的**，是原有架构的缺口。修它需要：
把 `RuntimeCommand` 的执行路径从 `tokio::process` 改成可注入的抽象，
iOS 下注入「调 `coomi_ish_run`」的实现（`ish_support.c` 已经写好了，
`ISHBridge.run()` 也已可用，缺的是**中间那层**）。

### P1：6 处死代码 —— 承诺的功能实际不存在

机械扫描（`work/deadcode.cjs`）结果，逐个人工确认后：

| 位置 | 名字 | 说明 |
|---|---|---|
| `ISHBridge.swift:79` | `isUserlandReady` | 「工作环境是否可用」的判断，无人用 |
| `ISHBridge.swift:290` | `shutdown()` | **内核起来后没人关它** |
| `ISHBridge.swift:301` | `unavailableReason` | 静态文案，无人用 |
| `ISHBridge.swift:314` | `installUserlandIfNeeded()` | 无人用（`bootWithReport` 内部直接调 `prepareFakefs`） |
| `ISHBridge.swift:407` | `runShell()` | **给外部执行命令的入口，零调用** |
| `ISHBridge.swift:415` | `hostURL()` | guest↔host 路径换算，无人用 |

`TarGzExtractor.swift:43` 的 `errorDescription` 是 `LocalizedError` 协议实现，
由运行时调用，**不算死代码**（已确认）。

`shutdown()` 与 `runShell()` 无人调用，和 #1 是同一个病根：
**桥接层写好了，但上层没有接**。

### P1：私有仓 CI 的 shell 变量 bug（已修）

私有仓 `build-ios.yml:97` 原本是：

```yaml
set +e          LIB=apps/coomi-rs/target/aarch64-apple-ios/release/libcoomi_ui.a
```

两条语句被挤到同一行。bash 里这是「把 `LIB=...` 作为 `set +e` 的临时环境变量」，
**`LIB` 不会成为 shell 变量**。实测复现：

```
$ LIB=[]                    ← 空
$ ls -la "$LIB"
ls: cannot access '': No such file or directory
```

后果：`ls`/`file`/`grep arm64` 三条断言全都在检查空路径，
`grep` 还会因 `file` 输出当前目录里含 arm64 的文件而**碰巧通过**。
加上 `set +e`，这步永远"成功"——**报告的成功是假的**。

公开仓同位置是正确的（两行分开），所以只有私有仓受影响。
已修复为两行，并写了 `work/yamllines.cjs` 扫同类问题（两仓现均无）。

### P2：文档里 2 处不成立的断言

| 文档原话 | 实际 |
|---|---|
| `ios_ffi.rs:8` 「只在需要 shell/git/python 时，把命令交给 iSH 执行」 | Rust 侧零引用，**没有这个交接** |
| `EngineController.swift:23` 「引擎与 iSH **完全解耦**」 | 「解耦」在这里是委婉说法，实际是**完全没接** |

「解耦」本意（引擎不依赖 iSH 也能跑）是对的，但读者会理解成「需要时能协作」。
这两句话都需要改成如实描述。

### C 侧 ABI 逐字段核对（关键：错位 = 静默内存踩踏）

结构体字段与 `ishembed.h` 完全一致：

```
ish_embed_boot_opts_t    rootfs_path, workdir, supervisor_guest_path,
                         kernel_log_fd, reserved_flags
ish_embed_spawn_opts_t   argv, cwd, envp, allocate_tty, merge_stderr_into_stdout,
                         timeout_ms, chroot_path, reserved_flags,
                         init_rows, init_cols, init_xpixel, init_ypixel
ish_embed_oneshot_result_t  exit_code, signal, stdout_buf, stdout_len,
                            stderr_buf, stderr_len, timed_out
```

C 侧用 `memset(&opts, 0, sizeof(opts))` 清零后只设有意义的字段，
`init_*` 四个字段在 oneshot 模式下保持 0（正确）。
函数签名（`ish_embed_boot` / `_run_oneshot` / `_free` / `_shutdown`）
与调用处逐参数匹配。
